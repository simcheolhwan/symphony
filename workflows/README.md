# 워크플로 시행착오

무인 실행 워크플로를 처음부터 쌓아 올리며 겪은 시행착오와 거기서 확정한 규칙을 기록한다. 각 항목은 겪은 문제, 원인, 확정한 규칙 순으로 서술한다. 프롬프트는 참조 없이 자기완결적이어야 하므로, 여기 규칙이 각 워크플로 본문에 반복되는 것은 의도된 중복이다.

## 공통 규칙

- 무인 세션 선언은 `무인 세션이다. 사람에게 중간 확인을 요청하지 마라.` 한 문장으로 고정하고, 모든 워크플로의 기본 원칙 첫 불릿에 그대로 쓴다. 사람과 다른 워크플로가 담당하는 역할 경계는 이 문장 뒤에 워크플로별로 덧붙인다.
- 최종 메시지의 첫 줄은 대상에 남은 관측 가능한 결과와 차단 요인의 1~3문장 평문 요약으로 고정한다. 헤딩, 목록, 코드 블록, 내부 서사(워크스페이스 복구, 절차 단계, 도구 호출)를 금지한다. 세부 내역은 둘째 줄부터 보고한다.
- 대상 설명이 비어 있으면 작업을 시작하지 않고 즉시 차단으로 처리한다. 설명 없는 대상은 요구사항을 복구할 근거가 없어 어떤 구현도 검증할 수 없다.

## 모든 워크플로가 겪은 문제

### 도구 승인 대기로 세션이 멈춤

Playwright MCP 등 추가 권한이 필요한 도구 호출이 나오면 세션이 승인 대기로 막혀 종료와 재시작을 반복했다. 무인 환경에는 승인 요청에 응답할 주체가 없고, 업스트림 기본값 `approval_policy: never`는 오케스트레이터가 모든 요청을 무조건 승인해 부적절한 요청까지 통과시킨다.

확정한 규칙: 승인 판단 주체를 Codex 자신으로 둔다. `approval_policy: on-request`와 `--config approvals_reviewer=auto_review` 조합으로 요청을 자체 검토해 승인하고, 부적절한 요청은 거절한다. 쓰기가 없어 승인 요청 자체가 발생하지 않는 읽기 전용 리뷰 워크플로만 `never`를 유지한다.

### 차단된 대상이 같은 실패를 반복

차단 사유를 기록한 이슈가 다음 폴링에서 다시 디스패치되어 같은 실패를 반복하며 토큰을 소비했다. 디스패치 조건이 `required_labels: [agent]`이므로 레이블 제거가 곧 디스패치 대상에서 스스로 이탈하는 수단이 된다.

확정한 규칙: 차단을 기록한 직후 에이전트가 스스로 `agent` 레이블을 제거한다. 승인 거절, 인증 실패, 정책 제한 등 원인과 무관하게 같은 방식으로 처리하고, 사람이 레이블을 다시 붙이면 재개된다.

### 참조 스킬이 대화형 확인을 전제

PR 생성 등 워크플로가 참조하는 스킬이 게시 전 미리보기 승인 같은 사용자 확인을 전제해 무인 세션이 진행하지 못했다.

확정한 규칙: 스킬은 생략 플래그(`--skip-preview` 등)로 확인 단계를 우회해 호출한다. 필수 정보나 권한이 없으면 사용자에게 질문하지 않고 차단 사유를 보고하고 끝낸다.

### 최종 메시지가 내부 서사라 알림 요약으로 쓸 수 없음

에이전트 최종 메시지가 워크스페이스 복구나 절차 단계 같은 내부 서사여서 알림 답글의 요약으로 쓸 수 없었다.

확정한 규칙: 위 공통 규칙의 첫 줄 요약 형식을 모든 워크플로에 건다. 프롬프트는 게시 채널(Slack)을 언급하지 않고 서술 제약만 건다. 채널은 표현 계층의 사정이고 에이전트에게는 제약만 전달해도 같은 산출물을 얻는다.

## linear가 겪은 문제

### 푸시 승인 기준이 없어 무한 재시도

auto review가 푸시 요청을 판정할 기준이 없어 거절과 재시도가 무한 반복됐고, PR 생성을 확인하지 않은 채 이슈가 `In Review`로 전환되기도 했다.

확정한 규칙: 승인 범위를 워크플로 기본 원칙에 선언해 auto review가 판정할 기준을 제공한다. 검증을 마친 현재 이슈 브랜치를 `origin`의 같은 이름 브랜치로 강제가 아니게 푸시하는 것만 승인하고, 기본 브랜치, 다른 원격, 강제 푸시, 브랜치 삭제는 승인하지 않는다. 승인 요청에는 게시 전에 확인한 푸시 대상, 로컬·원격 브랜치, 커밋 범위를 실제 값으로 적고, 범위를 벗어나거나 거절되면 재시도 없이 차단한다. 이슈는 PR 번호와 URL을 GitHub에서 확인해 Workpad에 연결한 뒤에만 `In Review`로 전환한다.

### 리뷰 대기 루프가 토큰을 상한 없이 소비

`In Review`에서 리뷰를 기다리는 폴링 루프가 세션을 유지했다. 대기 폴링 한 번이 모델 턴 하나이므로 `max_turns`가 구현 없이 소진되는 반면, 오케스트레이터의 트래커 폴링은 모델 호출이 아니어서 대기 비용이 0이다. 업스트림 원본도 같은 대기를 프롬프트로 지시하지만(`Human Review`에서 폴링하다 피드백이 오면 `Rework`로 전환) 그 상태를 active states에 넣지 않아 지시가 실행되지 않는다. 오케스트레이터는 실행 중인 이슈가 active도 terminal도 아닌 상태로 바뀌면 에이전트를 종료하므로, 에이전트가 스스로 `Human Review`로 전환하는 순간 자기 세션이 끝난다.

확정한 규칙: linear 워크플로의 책임은 Draft PR 생성까지다. `In Review`에 도달하면 즉시 종료하고 `In Review` 이슈는 픽업하지 않는다. 이후 리뷰 대응은 미응답 피드백을 감지해 디스패치하는 pr-author 워크플로가 이어받아, 토큰 소비가 사유 단위로 한정된다.

## pr-author가 겪은 문제

### 응답과 재요청을 남기지 않으면 왕복이 끊기거나 무한 반복

디스패치 사유에 관측 가능한 응답을 남기지 않으면 같은 사유로 무한 재디스패치되고, 대응을 마친 뒤 리뷰를 재요청하지 않으면 리뷰 왕복이 한 번으로 끊겼다.

확정한 규칙: 디스패치 사유마다 응답을 남긴다. 미해결 스레드에는 답글(무시 사유, 차단 사유 포함), 수정하지 않기로 판정한 CI 실패에는 PR 코멘트, 스레드 없는 `CHANGES_REQUESTED` 리뷰에는 수정 푸시 또는 PR 코멘트로 응답한다. 이번 실행에서 푸시하지 않았다면 최신 리뷰가 현재 head를 대상으로 하지 않고 리뷰 요청 목록에도 없는 사람 리뷰어에게 리뷰를 재요청한다. 판정은 세션 기억이 아니라 현재 PR 상태로 하므로 실행이 끊겨도 다음 실행이 이어받는다. 푸시한 실행에서 재요청하지 않는 이유는 푸시가 리뷰봇을 깨워 새 지적을 만들 수 있어서다. 리뷰봇이 조용하면 다음 디스패치가 재요청만 남은 상태로 같은 절차에 다시 들어온다.

리뷰 왕복의 전제조건도 여기서 드러났다. 대상 저장소의 `.github/CODEOWNERS`에 개인 계정 기본 리뷰어가 없으면 리뷰 요청이 자동 등록되지 않아 왕복이 시작되지 않는다. 리뷰어 트래커가 개인 앞 요청만 인식하므로 팀만 지정된 CODEOWNERS도 같다. 둘 다 차단 사유로 보고한다.

## pr-reviewer가 겪은 문제

### 구현과 같은 실행 설정이 클론과 턴을 낭비

읽기 전용 리뷰가 구현 워크플로와 같은 실행 설정을 써서 저장소 클론과 20턴 한도를 그대로 소비했다.

확정한 규칙: `hooks.after_create`를 두지 않아 워크스페이스를 빈 디렉터리로 남기고, 에이전트는 주입된 `github_api`로 PR과 코멘트를 읽는다. `max_turns`는 3이다. 리뷰, 제출, head 변경 시 한 번의 재실행이면 끝난다. 리뷰가 불완전하면 제출 없이 종료해 다음 폴링의 재실행에 맡기되, 세션 재시작으로 해소되지 않는 차단은 그 사유를 담은 `Needs discussion` 리뷰를 제출해 재디스패치를 멈추고 사람을 부른다. 관측 가능한 응답 없이는 같은 리뷰 요청이 무한 재디스패치되기 때문이다.
