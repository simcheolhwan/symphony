## 2-1. Linear 프로젝트 슬러그를 인스턴스마다 주입 `feature`

Linear 프로젝트가 워크플로 파일에 하드코딩되어 인스턴스마다 파일이 갈라지므로, 설정 해석에 환경변수 참조를 도입한다.

### 요구사항

- 워크플로 파일의 `project_slug`에 `"$VAR"` 참조를 쓰거나 `LINEAR_PROJECT_SLUG`로 주입할 수 있고, 런처 레지스트리의 `project` 필드가 주입한 값으로 Linear 폴링이 동작한다.

### 설계 결정

- 설정 해석 파이프라인에 `project_slug`를 편입하되 비밀값 해석과 별개인 일반 문자열 해석 경로를 신설한다. 비밀값 목록은 에이전트 프로세스 환경에서 해당 환경변수를 제거하는 목록이므로, 슬러그는 등록하지 않아 에이전트 세션에서도 읽을 수 있다.

## 2-2. GitHub PR을 작업 소스로 추가 `feature`

Linear 이슈만 작업 소스로 다룰 수 있어, 인증 사용자가 저자인 PR의 피드백 대응(`github_pr_author`)과 인증 사용자에게 온 리뷰 요청(`github_pr_reviewer`)을 처리하는 트래커를 추가한다.

### 요구사항

- 인증 사용자가 작성한 열린 PR(Draft 포함)에 미해결 리뷰 스레드, 실패한 Check Run, 인라인 코멘트 없는 `CHANGES_REQUESTED` 리뷰 중 미응답 건이 있으면 `github_pr_author`가 픽업한다. Check Run이 진행 중이면 완료까지 보류한다.
- 사람 리뷰어의 최신 리뷰가 현재 head를 대상으로 하지 않고 그 리뷰어가 리뷰 요청 목록에도 없으면 `github_pr_author`가 픽업한다. 리뷰봇 지적이 남아 있는 동안에는 그 지적이 먼저 사유가 되므로, 이 사유만 남는 시점은 리뷰봇이 더 이상 지적하지 않는 시점이다.
- 인증 사용자에게 직접 리뷰 요청이 온 열린 PR 중 아직 리뷰를 제출하지 않았고 CI가 통과한 PR을 `github_pr_reviewer`가 픽업한다. draft PR은 대상이 아니다.
- 에이전트가 디스패치 사유마다 GitHub에 관측 가능한 응답(리뷰 제출, 스레드 답글, PR 코멘트, 수정 푸시, 리뷰 재요청)을 남기면 다음 폴링에서 같은 PR이 다시 디스패치되지 않는다.
- 별도 토큰 관리 없이 로컬 `gh` 로그인만으로 폴링이 동작한다. 토큰을 얻지 못하면 인증 오류로 보고한다.
- 접근할 수 없는 저장소를 설정하면 폴링 단계가 아니라 기동 시점에 실패한다. 실행 중인 인스턴스가 설정을 reload하다 실패하면 오류를 보고하고 마지막 정상 설정으로 계속 동작한다.

### 설계 결정

- 어댑터 이름은 대상 PR이 아니라 인증 사용자의 역할 기준이다.
- 두 어댑터는 트래커 인터페이스와 GitHub 어댑터 공통의 2계층 구조(설정·도구를 위임하는 얇은 어댑터 + I/O를 담당하는 클라이언트)를 따르고, PR 목록과 Check Runs의 페이지네이션, 정규화는 공용 모듈이 담당한다. 각 어댑터는 후보 필터, 사유별 조회, dispatchable 판정을 소유한다.
- `github_pr_author`는 미해결 스레드 조회에 GraphQL이 필요하고, Draft PR도 후보에 포함해 피드백·CI 사유로 디스패치한다. Draft 상태 자체는 사유가 아니고 Ready 전환은 사람의 판단 게이트다.
- `github_pr_author`의 응답 판정은 두 축이다. 미해결 스레드는 마지막 코멘트 작성자가 인증 사용자인지로 스레드별 판정하고, 실패한 Check Run과 `CHANGES_REQUESTED` 리뷰는 인증 사용자의 마지막 활동 시각(코멘트와 제출 리뷰 중 최신) 이후 발생분만 사유로 삼아 응답 하나가 여러 사유를 동시에 소거한다. 두 사유는 현재 head에도 묶여 있어 수정 푸시가 head를 바꾸는 것으로도 소거된다. 푸시 자체는 활동이 아니며, 커밋이 기록되지 않은 리뷰는 head 변경을 관측할 수 없어 항상 현재 head 대상으로 간주한다.
- 사람 리뷰어와 리뷰봇은 리뷰 저자 타입이 Bot인지로 구분하고, 리뷰 요청 목록은 User 타입만 개인 요청으로 인정한다 (팀, 봇, mannequin 제외).
- 디스패치 사유가 없고 실패한 Check Run과 미해결 스레드도 남아 있지 않으며 사람이 현재 head를 승인했으면, `github_pr_author` 폴링이 이슈에 수렴 표시와 head sha를 실어 [수렴 알림](4-운영.md)의 감지 입력이 된다.
- 상태 폴링은 개별 PR의 dispatchable 판정 실패(피드백, 타임라인, Check Runs 조회 오류)를 그 PR 제외와 경고 로그로 격리해, 한 PR의 예상 밖 응답이 폴링 전체를 실패시켜 다른 PR의 디스패치까지 막지 않게 한다. id 조회는 호출자가 성공 응답에서의 누락을 소멸로 해석하므로 격리하지 않고 오류를 전파한다.
- `github_pr_reviewer`는 REST만 사용하고 인증 사용자 앞 직접 리뷰 요청만 인식한다. 팀 앞 요청은 픽업하지 못하며, 이 제약이 워크플로에 요구하는 CODEOWNERS 전제조건은 [워크플로 시행착오](../workflows/README.md)가 소유한다.
- `github_pr_reviewer`의 리뷰 제출 여부는 리뷰 존재가 아니라 최신 리뷰 요청 시각 이후에 제출한 리뷰가 있는지로 판정한다. 저자가 리뷰를 재요청하면 같은 PR이 다시 픽업된다.
- 인증은 공용 GitHub 클라이언트에서 설정값 → `GITHUB_TOKEN` → `gh auth token --hostname <host>` 순서로 해석한다. 미설정 토큰은 오류가 아니라 다음 순서로 폴백하고, `missing_github_token`은 `$VAR` 참조의 변수 이름이 부적격한 경우만 뜻한다. API URL의 호스트를 `gh`의 hostname으로 매핑해 GitHub Enterprise를 지원하고, `GH_PROMPT_DISABLED=1`로 대화형 프롬프트를 차단한다. 폴링 토큰이 에이전트 세션에 새지 않도록 GitHub 토큰 계열 환경변수는 비밀값 목록에 등록해 에이전트 프로세스 환경에서 제거한다.
- 저장소 접근 확인은 트래커 인터페이스의 선택 구현 preflight 콜백으로 두고 워크플로 로드의 마지막 단계에서 호출한다. GitHub 구현은 `GET /repos/{repo}` 1회로 401·403·404만 영구 실패로 분류하고 그 외(타임아웃 등)는 원래 오류를 전파한다. 구현은 공용 GitHub 클라이언트에 있지만 콜백은 PR 어댑터 두 개만 구현하므로 기존 Issues 어댑터에는 적용되지 않는다.
- preflight가 네트워크 요청이라 설정 읽기가 매번 파일을 다시 로드하던 방식을 유지할 수 없으므로, WorkflowStore는 읽기 요청에 캐시된 설정을 반환하고 reload는 1초 폴링과 명시적 `force_reload`에서만 수행한다. 읽기 호출은 타임아웃 없이 대기하므로 진행 중인 preflight 요청이 멈추면 설정을 읽는 호출도 그만큼 지연된다. 워크플로 파일 편집도 즉시가 아니라 폴 주기 안에서 반영된다.
