## 4-1. 인스턴스를 상시 운영하는 런처 도입 `feature`

Symphony 직접 호출이 복잡하고 인스턴스를 상시 운영할 수단이 없어 PM2 기반 런처 `symphonyctl`을 둔다. 명령, 설정, 주입 환경변수, 프로세스 모델의 명세는 [`launcher/README.md`](../launcher/README.md)가 소유한다.

## 4-2. 작업 이벤트의 Slack 알림 도입 `feature`

무인 실행 중인 작업의 시작, 차단, 강제 종료를 개입할 수 있는 시점에 알 수 있도록, 작업 이벤트를 Slack 스레드로 전달한다. 이벤트 규격, 스레드 정책, 템플릿의 명세는 [`notifier/README.md`](../notifier/README.md)가 소유하고, 여기는 발신 측인 오케스트레이터의 요구사항만 기록한다.

### 요구사항

- 작업이 시작, 재시도, 차단, 강제 종료, 실행 완료, 워크플로 종결, 사유 소진 대기, 수렴할 때 오케스트레이터가 알림 서버로 이벤트를 발신한다.
- `SYMPHONY_NOTIFY_URL`이 없으면 알림만 비활성화되고 실행은 그대로 진행된다. 값이 있는데 수신 측이 부팅을 허용하는 형식(`http://127.0.0.1:<포트>`)이 아니면 이벤트마다 경고 로그를 남기고 발신을 건너뛴다. 알림 전송이 실패해도 오케스트레이터 실행에는 영향이 없다.
- URL이 유효해도 `SYMPHONY_INSTANCE_NAME`이 없으면 이벤트를 발신하지 않고 경고 로그만 남긴다.

### 설계 결정

- Symphony가 Slack에 직접 접근하면 업스트림 머지 비용이 커지므로 발신과 전송을 분리한다. 오케스트레이터는 구조화된 이벤트만 발신하고, 포크 소유 `notifier/`가 Slack 토큰과 게시 로직을 전담한다.
- 알림은 오케스트레이터의 런타임 전환 지점에서만 발신하고, 트래커 상태를 비교하는 폴링 diff는 두지 않는다. 예외는 수렴이다. 수렴은 에이전트 실행 밖에서 사람과 CI가 만드는 상태라 대응하는 런타임 전환이 없으므로 폴링에서 감지하고, 발신한 head sha를 기억해 같은 head로의 재발신을 억제한다. 기억은 메모리 상태라 프로세스가 재시작하면 같은 head에 다시 발신할 수 있다.
- 머지도 사람이 만드는 상태지만 폴링 diff를 본격 도입하지 않도록, 수렴을 발신한 이슈가 이후 폴링에서 사라질 때만 그 이슈를 개별 조회해 terminal 상태면 종결 이벤트를 발신한다. 수렴에 도달하지 못한 채 닫힌 PR은 종결 알림 없이 끝나고, 이 확인도 수렴 기억에 얹혀 있어 프로세스 재시작 이후의 머지는 감지하지 못한다.
- 전송은 비동기 단발이고 재시도와 큐가 없다 (at-most-once). 상태의 원본은 트래커이므로 알림 유실을 허용하고, 전송 실패는 로그로만 남는다.
- terminal 이벤트 분류는 트래커 종류에 따른다. PR 트래커는 merged 여부로 워크플로 종결과 강제 종료가 갈리고, 그 외 트래커는 항상 워크플로 종결이다. 폴링 대상에서 벗어난 이슈는 PR 트래커면 사유 소진 대기, 그 외는 강제 종료로 발신한다. 차단 후 에이전트가 레이블을 뗀 이슈의 이탈도 강제 종료를 발신해, 재시도 없이 끝난 스레드의 종료 표시가 된다.
- PR 트래커에서 라우팅 소멸은 재디스패치 차단이지 실행 중단이 아니다. 에이전트의 수렴 행동(리뷰 제출, 수정 푸시)이 자기 디스패치 사유를 지우므로, 세션이 마무리 요약을 쓰는 수십 초 사이에 폴링이 그 소멸을 관측하면 강제 종료가 실행 완료 이벤트와 거기 실린 요약을 없앤다. 실행 중인 세션은 `draining`으로 표시만 하고 스스로 끝나게 두며, 정상 종료 시 실행 완료를 발신한 뒤 continuation 재시도 대신 사유 소진 대기를 발신한다. 즉시 종료는 terminal 전환(PR 머지, 닫힘)과 비 PR 트래커의 라우팅 회수(사람의 중단 지시)에만 남긴다. 무한 실행은 기존 stall 감지와 `max_turns`가 막으므로 별도 타임아웃을 두지 않는다.
- `retried`는 에이전트 실행이 실제로 실패한 경우로 한정해, 슬롯 부족이나 트래커 조회 실패로 인한 재스케줄이 같은 이슈를 반복 발신하지 않게 한다.
- 수행 내용 요약은 추가 LLM 호출 없이 운반한다. 오케스트레이터는 세션의 마지막 agent message 전문을 `agent_message` 필드에 실어 보낸다. 실행 완료와 차단이 주 경로이고, 실행 중인 세션을 강제 종료하며 발신하는 이벤트도 같은 전문을 싣는다. 첫 줄 요약 요구는 워크플로 프롬프트가, 첫 줄 추출과 절단은 notifier가 맡는다.
- 전송은 이벤트마다 태스크를 띄우므로, 한 전환이 연달아 발신한 두 이벤트는 도착 순서가 뒤집힐 수 있다. 수신 측은 도착 순서대로 스레드에 쌓으므로, 순서가 의미를 갖는 발신은 한 태스크에서 직렬로 보낸다.
- 발신할 이슈 스냅샷이 없는 이벤트는 로그 없이 버린다. 알림 문제가 그 이벤트를 만든 런타임 전환 자체를 방해하지 않기 위해서다.
- 수신 스키마의 `observed` 필드는 오케스트레이터가 관측한 상태 전환 목록을 위한 예약 필드이고, 발신 측은 아직 싣지 않는다.

## 4-3. 대시보드가 인스턴스를 식별하지 못함 `feature` `canceled`

### 요구사항

- 여러 인스턴스를 상시 운영할 때 상태 대시보드의 웹 페이지와 터미널 출력에서 어떤 인스턴스인지 이름으로 식별할 수 있다.
- 터미널 상태 출력이 안내하는 대시보드 URL이 로컬 바인딩 주소가 아니라 실행 머신 밖(tailnet)에서 접근 가능한 주소다.
